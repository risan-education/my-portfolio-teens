## どんな関心から始めるか

架空の高校生は、情報が多い学校サイトで予定を探しにくいと感じた。機能を増やす前に、利用者が何をしたいのかを確かめようとする。

- 関連を調べたい学部・学科の分野: **情報・情報工学**
- 高校生活を通して育てる大きな主テーマ: **利用場面から設計する情報システム**
- 最初の問い: **行事一覧の見出しと絞り込みを変えると、スマホやキーボード操作で日時・場所を探す手順はどう変わるか。**
- 準備・小さな始め方: 架空の行事データ、紙の画面案、可能ならローカルで動く簡単な試作。ログインや個人情報の収集なしで始める。

## 6段階の進め方

以下はすべて未実施の計画です。実際の記録では、本人が選んだ案・行ったこと・結果を分けます。

| 段階 | このテーマでの計画 |
| --- | --- |
| 1. 興味を見つける | 自分が探しにくかった情報と利用機器を記す。 |
| 2. 課題を決める | 「来週の校内行事の場所を見つける」など一つの利用課題を決める。 |
| 3. 仮説を立てる | 分類を増やすより、日付と場所を一覧に出す方が手順を減らせるのではと考える。 |
| 4. 現場で確かめる | 同じデータを使う二つの画面案で課題を試す。見つけられたか、迷った操作、キーボードだけで進めるかを確認する。 |
| 5. 形にして発信する | 改良した試作と設計理由を発表し、不具合と未対応の利用方法も示す。 |
| 6. 人を巻き込む | 情報の先生と友人で操作点検・内容点検を分担し、反応を基に改良する。学校サイトへの導入は別に管理者と相談する。 |

## 方法を具体的にする

データ量と課題を揃え、同じ画面を先に使った練習効果にも注意する。少数の利用確認だけで全員に使えると主張しない。AI生成コードは自分で動作と仕組みを確かめ、生成物と本人の設計・修正を分けて残す。

最初の学期は準備・予備調査・最初の改善までを目安に、授業や部活動と両立する時間を決めます。必要な協力が得られなければ、資料調査や紙の試作へ範囲を縮め、未実施の段階は理由と再検討日を記して残します。

## 予想と違ったらどうするか

次は**起こり得る展開の架空例**であり、結果の予告ではありません。

検索ボタンが増えて迷う人が出たら、多機能化を止めて情報の分類を見直す。紙の試作で判明した問題も、立派な検証結果として記録する。

## 高1からどう深めるか

高1は紙の画面で要件を確かめる。高2は実装して端末や入力方法の違いを点検し、改善を重ねる。高3は設計判断・検証・未解決の課題を整理する。

月ごとに次の行動を、学期末に主テーマと方法を見直します。ここに書いた学年配分は目安です。高2・高3から始める場合は範囲を絞り、実施していない過去を補わないでください。

**大学での学びとの接点:** ヒューマンコンピュータインタラクション、ソフトウェア工学、情報アクセシビリティ。コード量ではなく、問いと検証から設計を変えた過程を説明する。

出願用に整理するときは、本人が実際に取り組んだ問い・方法・変更・役割を原記録で確かめます。出願先の募集要項で活動の対象期間・評価方法・提出物・AI利用条件を確認し、[出願準備ガイド](../../docs/admissions-guide.md)に沿って許可された範囲だけ出力します。この架空例を本人の実績には含めません。

### 成果報告（架空）

私は、学校の行事情報を探すとき、必要な日時や場所が複数のページに分かれていることを不便に感じた。最初は検索機能を増やせば解決すると考えたが、利用者が何を探しているかを確かめずに作ると、操作を複雑にするだけかもしれない。そこで、来週の行事の場所を見つけるという一つの課題から画面を設計した。

架空の行事データを使い、日付と場所を一覧に出す案と、分類を選んで詳細を開く案を紙で作った。同意した友人に同じ課題を試してもらい、情報を見つけられたか、どの操作で迷ったかを記録した。私は画面案の作成と観察を担当し、情報の先生には、答えを覚える影響を小さくするため、課題や見る順番の設定を相談した。

点検では、分類が自分の考えと合わないと、どのボタンを選ぶか迷う場面があった。一覧に日時と場所がある案では詳細画面を開かずに答えられることがあったが、行事が増えると目当ての行を見失いやすくなった。私は、機能の数を増やすという方針を変え、まず一覧の並び順と見出しを整え、必要なときだけ絞り込める構成にした。

その後、個人情報を使わない簡単な試作を端末内で動かし、スマートフォンでの表示とキーボード操作を点検した。見た目では分からなかったが、キーボードだけでは一部の操作位置を確認しにくい問題が見つかった。先生と原因を調べ、操作中の場所を分かるように修正した。友人には修正した手順を再確認してもらい、残る問題を一覧にした。

授業内の発表では、完成画面だけでなく、紙の段階で捨てた案と変更理由を示した。成果は、利用課題から設計を見直した試作と、再点検できる問題一覧である。ただし、参加者と機器は限られ、全ての利用方法に対応したとは言えない。学校の公式サイトへの導入も行っていない。使ったコードについては、参考にした部分と自分で作成・修正した部分を区別して残した。

私は、動くものを作ることに加え、誰が何をできるようになったかを確かめる必要があると学んだ。紙の試作で見つかった問題も、開発を進める重要な根拠になった。今後は扱う情報量を変えて再点検し、大学では情報工学や利用者の行動を調べる方法を学びながら、設計の理由を説明できるシステムづくりを続けたい。
